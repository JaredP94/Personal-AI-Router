# Known issues

This page lists significant limitations, with what to expect and what to do
about them. This is not a bug tracker. Report anything not listed here as an
[issue](https://github.com/JaredP94/Personal-AI-Router/issues).
Report vulnerabilities privately as described in [Security](../SECURITY.md).

## Current Fork Release Is an Unsigned macOS Candidate

The latest published fork build, `0.7.0-rc.1`, targets macOS arm64 only. It is
unsigned/unnotarized; its privileged helper and helper-based firewall setup are
unavailable. Downloading via `curl` or verifying its checksum does not change
those trust restrictions. Windows/Linux desktop and Intel Mac runtime validation
remain outstanding for that candidate. See the [release notes](https://github.com/JaredP94/Personal-AI-Router/releases/tag/v0.7.0-rc.1)
for the exact tested scope; source-platform support is not artifact certification.

`nvpair-helper-ctl trust` checks the host app and the tool against helper code-signing
requirements; when not satisfied, PAIR skips the helper explanation dialog and registration
entirely (avoiding repeated prompts). In the desktop application, navigate to
**Settings → Service** to view the **Firewall setup: manual** card, which provides
guidance on allowing inbound connections when macOS prompts appear so other nodes
can reach this machine.

## Unified-Memory Systems Report Misleading GPU Memory

**Implemented in source, pending release testing.** GPU memory now has an explicit
kind rather than labeling every capacity as VRAM. This does not certify the
published `0.7.0-rc.1` assets. Current behavior depends on the collector:

| System / source | Kind and displayed memory |
| --- | --- |
| macOS Apple GPU (AGX class or `Apple ` name) | **Unified memory:** physical RAM capacity and GPU-mapped allocation (`Alloc system memory`), not whole-system RAM usage. |
| macOS non-Apple GPU | **VRAM** (`dedicated`): dedicated capacity and dedicated used counters only; system allocation is never substituted for VRAM usage. |
| Linux NVIDIA with numeric `memory.total` | **VRAM** (`dedicated`), from `nvidia-smi`. |
| Linux NVIDIA with `[N/A]` / `Not Supported` total (including UMA systems such as DGX Spark) | **Unified memory:** physical RAM capacity and system-used RAM. This is sentinel-based classification; used bytes are not GPU-only allocations. |
| Linux NVIDIA with malformed total | **Memory unavailable**; memory figures are omitted. Independently measured utilization can still appear. |
| Windows with dedicated video memory | **VRAM** (`dedicated`), plus a separate **Shared memory** budget and usage; these are never added together. |
| Windows with zero dedicated video memory | **Shared memory:** the shared-system-memory budget and measured shared usage, not dedicated VRAM or a claim of exclusive GPU capacity. |
| Linux AMD/Intel names-only inventory and other names-only platforms | **Memory unavailable**, without GPU utilization. Driver/collector support remains out of scope. |

Missing readings display `—`, not `0`; a measured idle `0` remains visible.
Unknown readings on one adapter do not hide measured readings on another. Memory
history breaks at missing samples rather than dropping to zero. Capacities and
usage are never summed across adapters, which may refer to the same system-memory
pool. Older peers without `memory_kind` display **Memory unavailable**, not
inferred VRAM.

**The impact is display, not routing.** Scheduling still uses pending work and
the maximum measured GPU utilization across adapters, not memory kind or capacity.
Invalid or stale telemetry retains neutral pressure. Use platform tools when
assessing whether a model fits: system RAM or a shared budget is not reserved
GPU memory. Windows runtime behavior is untested on this macOS verification host;
see [GPU memory semantics release testing](release-readiness.mdx#gpu-memory-semantics).

## Scheduling Is Not a Capacity or Latency Model

The scheduler ranks by pending work plus smoothed GPU-utilization pressure, then
pressure and stable UUID; stale/invalid telemetry gets neutral pressure. Proxies
also apply engine/model eligibility and prefix-affinity hints. This is not a
prediction based on GPU model, free memory, measured latency, or request cost.
A mixed-hardware cluster may therefore assign work to a slower eligible node;
a prefix-affinity preference does not prove an engine KV-cache hit.

The full list of gaps is in
[Scheduler Limitations](architecture.mdx#scheduler-limitations).
Improving this is on the roadmap, and knowing which signals matter on your
hardware would help. Refer to
[Roadmap](../README.md#roadmap).

## Worker Health: Manual Recovery and Platform Limits

The broker probes all twelve workers, marks them `degraded` after two consecutive
failed probes, and restarts eight eligible workers after three. Engine-manager
and the three proxies are **never auto-restarted on a hang**: doing so could
orphan engines or interrupt inference streams. Their degraded desktop rows show
"Not responding — restart manually" under **Settings → Service → Workers**.
Restarting engine-manager may leave engines running or stop them; proxy restarts
interrupt inference. Desktop asks for confirmation for these four workers; TUI
**Overview** offers `R` with confirmation for any selected worker.

Optional initial spawn failures now use bounded retries shared with crashes and
eligible hangs. Exhausted workers need an explicit restart; missing default
binaries remain `missing` until an explicit retry finds them. Health proves
control-loop responsiveness, not domain progress or HTTP/inference readiness.
See [Health and Failure Detection](architecture.mdx#health-and-failure-detection).

Cross-process hang tests use Unix signals and are Unix-only. Windows hang
recovery remains unproven; unit tests are not cross-process Windows evidence.

The broker-client layer remains separate: a 15-second heartbeat and 45-second
inbound-silence deadline support frontend-owned recovery with a readiness deadline.
This is not a guarantee that every unexpected broker exit automatically reconnects.

## macOS Can Stop Answering LAN Connections While Unclustered

On macOS, PAIR can stop answering connections from other machines on the network
after it has been left unclustered for a while. Other nodes stop being able to
discover or reach it, while the application itself looks healthy. Restarting PAIR
restores it. This is a rarer problem than the others on this page, and it has only
been seen on macOS.

## The Terminal Interface Cannot Do Everything the Desktop App Can

`nvpair-tui` is an operations tool for headless machines rather than a full
replacement. It cannot do any of the following:

- List or delete models
- Change an engine's port
- Update an engine
- Control engines on other nodes
- Show which node served a workload

This matters most for a genuinely headless deployment, where those operations have
no other route on that machine. Refer to
[What the Terminal Interface Cannot Do](terminal-interface.mdx#what-the-terminal-interface-cannot-do).

## Engine Binaries Are Not on Your PATH

PAIR does not add the engines it installs to your `PATH`, so running an engine's
CLI means using the full path. Refer to
[Using an engine's own command line](getting-started.mdx#using-an-engines-own-command-line)
for the locations. This is on the roadmap.

## Platform Limits Worth Knowing

- **The Linux desktop installer is a `.deb` only.** On RPM-based distributions,
  [build from source](building.mdx).
- **Windows on ARM is experimental.** Refer to
  [What is supported](../README.md#what-is-supported).
