# Performance and Energy: Upcoming Release

## Release-Candidate Profile (2026-10-20)

The unsigned macOS arm64 `0.7.0-rc.2` candidate was profiled against the published
`0.7.0-rc.1` with the [release profiling harness](../scripts/perf/README.md). This is the
`0.7.0-rc.2` comparison; **no profile has been recorded for the current
candidate**. It is a partial gate result, not a certified
benchmark: the inference scenario and tracing-enabled runs were not measured (see
[What Was Not Covered](#what-was-not-covered)).

**Result:** in this setup the candidate uses about the same CPU and memory as rc.1. Idle
GPU sampling now relaxes to its 10-second rate, so the candidate's `ioreg` collector costs
the same as rc.1's. Package idle wakeups are higher in the candidate, and the cause has not
been established.

### What the Numbers Show

- **Idle sampling works as designed.** Tray only, with no workloads, the candidate's
  sampling falls back to 10 seconds, the same cost as rc.1. Before the fix in
  [#13](https://github.com/JaredP94/Personal-AI-Router/pull/13), a tray-only candidate
  sampled every 2 seconds (`ioreg` 1.66% against rc.1's 0.35% in a diagnostic run).
- **No measured saving against rc.1 in this setup.** The earlier development rounds below
  were measured on a real clustered installation with live peers, where trust refresh,
  discovery and alias handling do much more work. A fresh unclustered node gives most of
  those changes nothing to act on, so this profile neither confirms nor refutes them.
- **Package idle wakeups rose from about 0.4 to 2.3 per second.** They are spread across
  several workers (job scheduler, the three proxies, cluster manager). The new 30-second
  worker health checks are a plausible contributor, but the cause is not established. The
  increase is small next to roughly 300 interrupt wakeups per second.
- **Older peers can hold a node at the fast rate.** An rc.1 peer polls
  `/v1/node-info` without `X-NVPAIR-Poll`, and node-info treats a missing header as
  `foreground`. While any rc.1 node on the LAN polls a candidate node, that node samples its
  GPU every 2 seconds. Diagnostic runs measured `ioreg` at 1.66% in this situation. Idle
  backoff applies once every peer is upgraded.

### What Was Not Covered

- Controlled inference and tracing-enabled runs (gate step 2).
- Clustered nodes, engines, and routing eligibility, freshness or alias failover checks
  during the runs (gate step 5).
- GPU utilization counters, file growth, and physical power. The kernel billed-energy counter
  is recorded by the harness but is not reported here, because its units and attribution
  are unvalidated.
- Windows and Linux.

Publishing a percentage improvement for this release still requires those scenarios.

## Historical Development Rounds

These are **development observations from three profiling rounds run during the
release work** on the published `0.7.0-rc.1` app (Round 1) and two patched
development builds (Rounds 2 and 3). They are not fresh measurements of the
corrected `0.7.0-rc.2` candidate and must not be presented as a certified
benchmark: raw samples, power state, and complete build identities were not
retained.

**Unattended idle backoff is restored behind scheduling leases; the
[release-candidate profile](#release-candidate-profile-2026-10-20) confirms it reaches the
idle rate.**
An earlier Round 3 attempt let scheduling polls read cached GPU snapshots without
coordination, which risked exceeding the scheduler's 10-second freshness budget and was
reverted. That unattended idle backoff has now been architecturally restored:
`nvpair-node-info` uses explicit `X-NVPAIR-Poll` leases (`foreground`, `scheduling`,
`background`) and broker demand signaling (`stats/set-demand`), relaxing sampling to
10 seconds when idle while keeping scheduler decision-point freshness proven <= 8.5 seconds.
Reaching that idle rate depends on nothing renewing a lease it does not need, which is
why the broker now also owns the scheduling lease (`telemetry/set-scheduling-demand`)
instead of both pollers renewing it unconditionally, and why a tray-only desktop session
reads node-info as background. Neither change alters node-info's policy constants or the
scheduler's freshness budget; both were profiled only as part of this work, so the
quantitative rows below remain historical.
In addition, `nvpair-manual-nodes` delivers scheduling telemetry every ~2 seconds
separately from 10-second topology probes. Because this coordinated implementation was
completed after the historical profiling rounds, rows marked **†** (dominated by the
earlier prototype) cannot be taken as measurements of the current code. The candidate must
be re-profiled on final release artifacts before publishing quantitative performance claims;
the [release-candidate profile](#release-candidate-profile-2026-10-20) above is that profile
for the tray-only and Overview scenarios.
Unmarked Round 3 improvements come from changes the candidate keeps (network-event
monitoring, trust-pin caching, warning deduplication, TLS-aware probing).

### Reading These Numbers

- Wakeups and avoided I/O are energy-related indicators, not watts or battery
  runtime. The kernel billed-energy counter's units and attribution were not
  validated; treat its −96% as directional only, and note it is dominated by the
  historical sampling experiment.
- "0 in sample" means no writes during that window, not a zero-I/O guarantee.
  Real warnings and debug-level logging still write.
- Remaining idle activity is intentional: two-second trust-directory checks in
  seven workers, two-second scheduling telemetry delivery (the GPU collection
  behind it relaxes to ten seconds only while no workload is queued or running),
  one-second CPU/memory sampling, and mDNS loops.
- Short samples, warm-up, background load and power state limit causal claims.

## Final Artifact Profiling Gate

The retained [release profiling harness](../scripts/perf/README.md) collects reproducible macOS arm64 artifact comparisons and documents the gate checks that still require controller evidence.

Before publishing a new quantitative release claim:

1. Preserve the baseline and final artifact hashes, source commits, service
   versions, harness, machine/OS/GPU details, power source/mode, screen state,
   cluster/peer versions, collector settings, engines/models, and workload.
2. Use equivalent warm-up and topology; alternate baseline/candidate runs with
   at least five repetitions per scenario and at least 120 seconds of steady
   sampling after warm-up. Test tray-only, visible Overview, and controlled
   inference, with tracing both disabled and enabled in its supported modes.
3. Discover and sample the whole owned process tree dynamically, including
   short-lived hardware collectors. Separate app CPU, child CPU, GPU counters,
   physical footprint, RSS, logical writes, file growth, and wakeup counters.
4. Measure physical energy/power only with a documented, supported instrument
   and attribution method. Otherwise report the energy proxy metrics explicitly,
   without converting kernel billed-energy counters into battery claims.
5. Report per-run data, median and spread, failures/skips, and sampling limits.
   Verify routing eligibility, telemetry freshness and alias failover during the
   same scenarios; a lower counter with broken scheduling is not an improvement.
6. Inspect the final candidate and repeat profile/lifecycle checks after any
   runtime correction. A build or component test is not a packaged-runtime pass.

Do not replace the installed application, alter real cluster membership, start
engines, or enable payload capture solely to produce a benchmark without an
explicitly authorized test environment.
