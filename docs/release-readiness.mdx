### Effective Tracing and Privacy Controls

**Implemented on this branch (pending release testing).**

- **Dynamic Broker Configuration:** Proxies start with tracing disabled and do not
  read ambient environment variables (`PAIR_TELEMETRY_*`, `OTEL_*`). Settings are
  persisted in `nvpair-node-settings` (schema 2) and reconciled by the broker dynamically
  via `telemetry/configure`.
- **Explicit Informed Consent:** Content capture defaults to off and requires explicit user
  consent (`payload_consent_version: 1`). Migration resets tracing and capture to off.
- **Strict Local Boundaries:** Tracing is local-only; serving nodes record no spans for
  peer-originated requests, W3C trace context is stripped before forwarding, request headers
  are allowlisted strictly to `Content-Type` and `Content-Length`, and captured payloads
  are truncated to 16 KB UTF-8. Exporters dial loopback `127.0.0.1:<collectorPort>`.
- **Managed, Loopback-Only Phoenix:** Phoenix is managed by the broker from an embedded
  template pinned to digest `sha256:c542e7de1dc1fdd0f938de337d44ebefa7266e91391eed6e7978523d7f6e1f2f`,
  binding exclusively to `127.0.0.1:6006` and `127.0.0.1:<collectorPort>`. The in-app update
  feature and custom compose paths have been removed.
- **Trace Storage Measurement & Scoped Purge:** Trace volume storage is reported in the
  desktop UI and can be purged via `telemetry/purge-storage` (`{confirm: "delete-traces"}`),
  safely clearing only `nvpair-phoenix-data` volumes without force-removing containers or
  pruning foreign Docker resources.
- **No Collector Advertisement:** The `otel=4317` TXT advertisement was removed from discovery.
  See [Security](../SECURITY.md#opentelemetry-and-phoenix-boundaries-and-privacy-controls).

### Scheduling Telemetry and Idle Sampling

**Implemented on branch release/protocol-sampling (pending release testing).**

- **Lease-Driven Sampling:** Node-info hardware collection uses `X-NVPAIR-Poll`
  request leases (`foreground`, `scheduling`, `background`) and broker demand
  signaling (`stats/set-demand`). On macOS and Linux, hardware GPU sampling runs
  every 2 seconds during interactive UI use or active workload execution, 5 seconds
  during scheduling demand (when local or remote workloads exist or are queued),
  and relaxes to 10 seconds when fully idle. Windows retains its native 1-second
  PDH collector loop.
- **Demand-Gated Scheduling Leases:** The broker owns the scheduling-demand
  decision (`telemetry/set-scheduling-demand`), because it is the only process
  that sees every workload: it pushes `{active:true}` on the first non-terminal
  workload in its store — queued or running, local or peer-origin, including a
  local in-flight inference request, which is recorded as a workload — and
  `{active:false}` when the last one reaches a terminal state or is removed. The
  scanner and `nvpair-manual-nodes` keep their own poll cadence but choose the
  lease they renew from that value: `scheduling` while active, `background` (which
  renews nothing) otherwise. Both workers start inactive and are re-told on every
  respawn, so neither a restart nor a two-second poll can hold a node above its
  idle cadence. A desktop session with no window — tray-only — is a background
  reader for the same reason: the tray icon is not a window, and the tray popup
  counts only while it is shown.
- **Cold-Start Transition:** Demand can turn on between two polls, so the first
  scheduling sample after a fleet goes from idle to busy can be up to the idle
  cadence old. That sample is not re-stamped: the scheduler keeps its 10-second
  freshness budget and applies neutral pressure to a sample it cannot vouch for,
  never a younger age than the sample has.
- **Freshness Budget Preservation:** Sampling operations use a 1-second collection
  timeout. Telemetry age at the scheduler's decision point is mathematically and
  empirically proven <= 8.5 seconds across all valid lease and scheduling modes,
  strictly preserving the scheduler's 10-second freshness budget.
- **Sample Identity and Deduplication:** Node-info stamps each hardware reading
  with a monotonic `sampleSeq` counter, carried across discovery records and
  broker feeds into `nvpair-job-scheduler`. Repeated observations carrying an
  identical non-zero `sampleSeq` do not re-weight the EWMA.
- **Decoupled Manual Node Telemetry Delivery:** `nvpair-manual-nodes` delivers
  `node/telemetry` notifications every ~2 seconds (± 250 ms jitter) over reused
  HTTP connections, reporting honest sample age (including probe and sample
  latency), completely separate from slower 10-second topology and model probes.

### Desktop Relay Envelope Validation

**Implemented on branch release/protocol-sampling (pending release testing).**

- **Canonical Envelope Enforcement:** Desktop's `JsonRpcSubprocess` and
  `relay-envelope.ts` scanner enforce canonical JSON-RPC 2.0 / relay v2 envelopes.
  Duplicate and case-variant reserved members (`jsonrpc`, `id`, `method`,
  `params`, `result`, `error`, `epoch`, `seq`) are rejected as recoverable decode
  errors, verified against the shared cross-process corpus
  `services/shared/jsonrpc/testdata/envelope-conformance.jsonl`.
- **Lossless Sequence Parsing:** Sequence numbers (`seq`) are decoded losslessly
  as `bigint` without IEEE-754 precision loss for numbers exceeding 2^53 - 1.
- **Inbound Silence Preservation:** Malformed frames are dropped as decode errors
  without resetting the 45-second inbound silence reconnect deadline.
- **Clean Termination on Protocol Mismatch:** Any relay protocol envelope
  mismatch (missing or wrong-typed stamps on notifications, or unexpected stamps on
  requests/responses) terminates the broker session cleanly, fails all pending
  calls, and reports a supervisor crash with `{ protocolMismatch: true }` without
  attempting an automatic reconnect.
- **Legacy Fallback Removed:** The legacy `broker:epoch` params fallback for
  envelope epoch discovery has been completely removed.

### Worker Health

**Implemented, pending release testing.**

- All twelve workers answer `worker/health`; the broker probes every 30 s with a
  5 s deadline (`--worker-health-interval`, minimum 1 s; deadline capped at the
  interval). Two consecutive failures report `degraded`; a successful probe
  restores `running` and clears the failure count.
- Three failures restart only scanner, errors, settings, node-info,
  workload-manager, manual-nodes, cluster-manager, and scheduler. Engine-manager
  and the three proxies never auto-restart on a hang: orphan/stream safety is not
  established. Desktop shows "Not responding — restart manually" for those rows.
- Optional initial spawn failures, crashes and eligible hang restarts share
  1 s → 16 s backoff and five replacement attempts. Healthy reset needs 60 s
  uptime and a successful probe since spawn. Missing default binaries remain
  `missing` with no automatic retry until `workers:restart` finds them. Scanner
  initial failure and invalid explicit paths remain fatal.
- `workers:get-status`, `workers:restart`, and full `workers:update` snapshots
  drive Settings → Service → Workers and TUI Overview (all twelve workers, `R`
  with confirmation). Clients recover worker snapshots after epoch changes;
  the 15 s broker heartbeat / 45 s client-silence layer remains separate.
- Cross-process hang tests are **Unix-only; Windows behavior remains unproven**.
  Passing source checks is not final-artifact or release testing. Verify packaged
  startup/retry, manual confirmation and recovery on each release platform before
  classifying this item resolved for that release.

### GPU Memory Semantics

**Implemented, pending release testing; Windows runtime untested on this host;
Linux AMD/Intel remain names-only.**

- Go reports `dedicated`, `unified`, `shared`, or `unavailable` per adapter.
  Apple unified usage is GPU-mapped allocation; Linux NVIDIA unified usage is
  system-used RAM. Unified detail reads `<used> used of <total> unified memory`.
  macOS Intel GPUs report a shared budget, while AMD/NVIDIA discrete GPUs remain
  dedicated; neither substitutes system allocation for dedicated-used counters.
  Windows dedicated VRAM and shared-system-memory budgets/usage
  are separate; zero-dedicated adapters report shared memory, not VRAM.
- Discovery/manual-node/broker propagation and desktop history preserve missing
  readings separately from measured zero. Labels follow the reported kind;
  unknown current readings show `—`, charts break at gaps, and adapter memory is
  never summed. Older peers without a kind render unavailable memory.
- Scheduler policy is unchanged: maximum measured utilization, neutral pressure
  for invalid/stale telemetry, no memory-capacity ranking. Linux AMD/Intel driver
  collectors are out of scope and remain **Memory unavailable**, without GPU
  utilization.
- Windows host-runnable classification/counter fixtures and cross-compilation
  are not actual DXGI/PDH execution. Verify real adapter capacities, independent
  dedicated/shared counters, idle/unknown readings, multi-adapter displays, and
  packaged history recovery on release platforms before calling this resolved
  in a release. Source checks do not certify published assets. See
  [GPU memory limitations](known-issues.mdx#unified-memory-systems-report-misleading-gpu-memory).

### Terminal interface operations

**Implemented, pending release testing.**

- Engine-manager reports effective per-host capabilities from manifests, platform
  and ownership. Desktop and TUI consume those flags; missing flags default to
  false. oMLX pull/delete remain unsupported and its server port is not editable.
- TUI Engines offers node selection (`n`), model inventory (`m`), supported
  pull/delete (`p`/`d`), local server-port editing (`e`), and destructive update
  by reinstall (`U`). Peers support install/start/stop and supported model
  pull/delete; restart/uninstall/update/persistent port changes remain local-only.
- Model deletion, uninstall, update, port changes, cluster removal/leave and
  manual-node removal require default-cancel confirmation with frozen targets.
  Update never installs after failed uninstall; it has no rollback guarantee.
  Long-operation deadlines include an 11-minute uninstall allowance inside the
  overall 31-minute update budget.
- Workloads show distinct origin and destination, with friendly-name/UUID-prefix
  fallback and destination replacement on failover. Assignment is not proof of
  completed inference. Built-in inference submission remains out of scope.
- Automated checks use fake engines, brokers, transports and temporary service
  processes. **Live engines and clusters were not exercised.** Before calling
  this resolved for a release, test packaged interactive terminals on release
  platforms, destructive update/uninstall and file retention, port restarts,
  model deletion/restart failures, slow remote install/pull, offline/trust
  errors, discovery inventory lag, and multi-node workload failover. Passing
  source checks do not certify released artifacts. See
  [terminal interface usage](terminal-interface.mdx).
